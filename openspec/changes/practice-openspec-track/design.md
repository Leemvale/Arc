## Context

В репозитории есть продуктовый контекст и OpenSpec, но нет приложения, базы или существующего API. Мотивация и продуктовые границы описаны в `proposal.md`; поведение — в четырёх delta specs этого изменения.

Согласовано: первая версия локальная, один пользователь, без авторизации; OpenAI API, $5 на эксперименты; оценённые ответы неизменны, повторная практика в новой сессии; незавершённая сессия восстанавливается. API-ключ и отдельный API-биллинг пока не подтверждены. Реальные вызовы нужны для приёмки качества, но не для разработки остальных частей.

## Goals / Non-Goals

**Goals:** единый TypeScript стек, надёжные переходы сессии, воспроизводимый контент, валидируемая обратная связь и ограниченные расходы. Design нужен из-за новой архитектуры, базы и внешнего провайдера.

**Non-Goals:** распределённая очередь, отдельный сервис оценщика, streaming, tool calling и глобальный клиентский store; они не нужны для пяти последовательных заданий одного пользователя. Продуктовые исключения перечислены в proposal.

## Decisions

### 1. Локальный веб-интерфейс и сервер

Использовать React + TypeScript + Vite, TanStack Query для серверного состояния и локальное состояние React для формы. Zustand/RTK пока не добавлять: сохраняемое состояние принадлежит серверу, а форма одному экрану. Сервер — Node.js + TypeScript + Fastify, PostgreSQL с SQL-миграциями и драйвером `pg`; Zod для границ контента, API и результата AI. Сервер вызывает OpenAI через AI SDK. Версии зависимостей фиксируются lockfile при реализации после проверки совместимости.

В разработке Vite проксирует `/api` на локальный сервер; сборку интерфейса отдаёт тот же сервер. Сервер, Vite и порт PostgreSQL привязываются к loopback. PostgreSQL запускается через Docker Compose с постоянным volume. Ключ хранится только в серверном окружении, не в переменных `VITE_*`, репозитории или логах. Изменяющие запросы принимаются только с ожидаемого локального Origin и JSON Content-Type; CORS не открывается произвольным сайтам.

Альтернативы: SQLite проще по установке, но PostgreSQL соответствует исходному направлению и даёт транзакции для конкурентных отправок; full-stack framework добавляет соглашения без необходимости SSR. Авторизация и внешнее размещение потребуют отдельного изменения.

### 2. Версионированный пакет контента

Хранить пакет трека в репозитории как типизированные данные: `trackId`, `contentVersion`, `sourceCommit`, контекст профиля/версии, навыки, пять упражнений и справочник источников. Упражнение содержит `id`, `type`, `skillId`, `prompt`, критерии `{id, description}`, `sourceIds`, выдержки источника и подготовленное объяснение; multiple choice дополнительно содержит варианты и правильный `optionId`. Ключ ответа и рубрика оценщика не выдаются до отправки ответа; разбор доступен после оценки.

Перед написанием контента закрепить существующий полный SHA upstream Fission-AI/OpenSpec, прочитать по нему три документа из product-context и проверить постоянные ссылки. Конкретный SHA выбирается в задаче подготовки контента; здесь не создаются формулировки учебных заданий и не предполагается совпадение upstream с установленным форком CLI. Набор из двух multiple choice и трёх open answer — рабочее проектное решение для покрытия трёх учебных областей.

Пакет проходит валидацию до использования. Каждая сессия хранит полный неизменяемый snapshot пакета, включая источники, чтобы продолжение и история не зависели от новых релизов контента. Для первой версии дублирование пяти заданий проще, чем каталог миграций контента. Во время оценки нет загрузки документов из сети, парсинга или RAG.

### 3. Данные, состояния и API

Основные таблицы:

| Таблица               | Назначение и ограничения                                                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `sessions`            | UUID, track/content version, snapshot, `active/completed`, current position, revision, даты; partial unique index на активную сессию трека  |
| `answers`             | session + exercise unique, неизменяемый текст/optionId, состояние `submitted/evaluating/failed/assessed`, дата принятия                     |
| `assessment_attempts` | answer, attempt UUID, состояние, deadline, ошибки, модель/prompt/rubric version, токены, резерв и расход; одна действующая попытка на ответ |
| `assessments`         | answer unique, критерии, категория, объяснение, sourceIds, дата; только валидный учебный результат                                          |
| `experiment_budget`   | единый бюджет USD, лимит по умолчанию 5, потрачено и зарезервировано; используется приложением и eval runner                                |

Ввод до отправки сохраняется синхронно в localStorage по session/exercise при каждом изменении. Наличие server answer имеет приоритет над старым черновиком. Черновик удаляется только после подтверждения серверного сохранения. Ошибка localStorage показывается явно; очистка данных браузера вне гарантии восстановления неотправленного текста. Серверные данные переживают перезапуск благодаря PostgreSQL volume.

API:

- `GET /api/track`: описание, карта, активная сессия, история.
- `POST /api/sessions`: создать сессию или вернуть существующую активную.
- `GET /api/sessions/:id`: восстановить шаг, ответ, состояние оценки, доступный разбор.
- `POST /api/sessions/:id/answers`: принять ответ текущему заданию; повтор того же payload возвращает существующее состояние, конфликт — 409.
- `POST /api/answers/:id/retry`: новая техническая попытка только для `failed`; для `evaluating` возвращает состояние, для `assessed` — готовый результат.
- `POST /api/sessions/:id/advance`: шаг вперёд с ожидаемой revision и exerciseId; повтор не должен перескочить через задание.
- `GET /api/sessions/:id/result`: сохранённый итог завершённой сессии; для активной — 409 с состоянием сессии.

Сервер валидирует всё независимо от UI. Ответ принимается в транзакции; создание job фиксируется до ответа 202. Локальный обработчик забирает записи попыток из БД, выполняет вызов вне транзакции и сохраняет итог отдельной транзакцией. Redis не нужен. Фоновая обработка не зависит от открытой вкладки; UI опрашивает состояние через TanStack Query.

На 1–4 заданиях валидная оценка оставляет экран обратной связи до «Далее»; на пятом сохранение оценки и завершение сессии атомарны. Пятая обратная связь входит в экран результата. Проверка revision защищает переходы из двух вкладок.

У попытки жёсткий таймаут вызова 60 секунд и deadline 90 секунд с момента начала обработки. На перезапуске незавершённая попытка становится `failed` по deadline; автоматический повтор запрещён. Поздний ответ старой попытки не может перезаписать результат новой: запись допускается только для текущего attempt UUID. Внешний провайдер может завершить запрос после локального таймаута; гарантируется одна принятая учебная оценка, а не exactly-once выполнение у провайдера.

### 4. Оценщик и обратная связь

Начальный кандидат — `gpt-5.4-mini-2026-03-17`, без дополнительного reasoning. Это выбор для проверки качества, не обещание точности. Модель доступна через конфигурацию сервера; смена модели или промпта требует полного повторного eval. [Официальная карточка модели](https://developers.openai.com/api/docs/models/gpt-5.4-mini) подтверждает structured outputs и snapshot; тариф, проверенный при планировании 2026-10-11: $0.75/1M входных и $4.50/1M выходных токенов. Перед реальными запусками перепроверить тариф и доступность в API-аккаунте.

Запрос включает системные правила оценивания, точную рубрику, выдержки и ответ в отдельном поле недоверенных данных. Возвращаемая структура: `criteria[{criterionId, met, explanation}]`, `understood[]`, `missingOrIncorrect[]`, `explanation`, `sourceIds[]`. Схема запрещает лишние поля, пустые обязательные объяснения и неизвестные значения; дополнительные проверки обеспечивают точное множество критериев и допустимые sourceIds. Категорию вычисляет сервер. Произвольные URL модели не используются. Multiple choice имеет один бинарный критерий и подготовленную обратную связь, поэтому его категория — «верно» или «неверно».

На сервере ограничить ответ ученика 8 000 символами, полный вход оценщика 12 000 токенами и выход 1 500 токенами; слишком длинный ввод отклоняется с пояснением и сохраняется в форме. Ограничения являются проектными стартовыми настройками. AI SDK не должен делать автоматические retries. Отказ, некорректная структура, обрыв по лимиту и недоступность API дают `failed`, а не учебную оценку.

Альтернатива — свободный текст и категория от модели — усложняет проверку и может расходиться с рубрикой. Итог навыков строится детерминированно из сохранённых критериев и не требует дополнительного вызова AI.

### 5. Расходы и оценка качества

До вызова в транзакции резервировать верхнюю стоимость разрешённого входа и выхода по актуальному тарифу. Для выбранных лимитов это $0.01575 на попытку без скидки кэша. Не допускать вызов, если `spent + reserved + newReserve > 5`. Вход должен быть посчитан совместимым tokenizer с учётом сообщений и схемы; до подтверждения корректности подсчёта использовать консервативный резерв. При неизвестном тарифе вызов блокируется.

После успешного ответа сверять usage и заменять резерв реальной стоимостью; при таймауте или неопределённом биллинге считать весь резерв израсходованным. После сбоя сохранения резерв не освобождать без сверки. Это локальный консервативный учёт, а не гарантия полного счёта OpenAI: посторонние вызовы с тем же ключом и изменения тарифов в него не входят. Рекомендуется отдельный API-проект для эксперимента. Повышение лимита — отдельное явное действие пользователя; автоматического сброса счётчика нет.

Eval runner использует тот же оценщик и бюджет, но отдельные входные fixtures, не учебные сессии. Сохранить 18 эталонных ответов и минимум три проверки инструкций обойти рубрику; выполнить два прогона фиксированной конфигурации, отдельно посчитать валидность структуры, совпадение критериев и категорий. Разобрать каждое расхождение по источнику и сохранить отчёт с моделью, версиями, результатами и расходами. Порог — спецификация `answer-assessment`; нельзя объявлять приёмку выполненной по мокам. Эталоны утверждаются до запуска и не подгоняются под модель.

### 6. Результат и проверка сценария

Три маршрута UI: трек, сессия, результат сессии. История находится на странице трека. Группировка критериев по skillId и ссылки на ответы формируют итог без числового mastery и без агрегации разных сессий. Источники берутся из snapshot. Не требуется отдельная аналитическая таблица: сохранённых оценок достаточно для воспроизводимого результата.

Проверить интеграционно транзакции, повторную отправку, конкурентные вкладки, просроченные попытки и резерв бюджета. В браузере пройти основной цикл и перезагрузки до отправки, во время проверки, после оценки и после завершения. Технические сбои воспроизводить fake provider; качество оценивания проверять отдельно реальными вызовами. После первой личной тренировки записать качественную обратную связь об объяснениях, спорных оценках и обнаруженных пробелах, без утверждения об эффективности обучения.

## Risks / Trade-offs

- Ошибка AI при валидной структуре → содержательные eval, объяснения по критериям и ссылки; результат сессии не трактуется как устойчивое владение навыком.
- Потерянный ответ провайдера может потребовать ещё одного оплаченного запроса → явный retry, консервативное списание резерва и защита от поздней записи.
- Документация upstream отличается от рабочего форка → закреплённый commit, подпись контекста и ручная проверка рубрик до публикации пакета.
- $5 может не хватить при многократной настройке → общий лимит тренировок/eval и отчёт; увеличение только по решению пользователя.
- API пока не настроен → полезные локальные экраны и mocked tests доступны, но полная приёмка блокируется до реального eval.
- Локальное приложение зависит от PostgreSQL/Docker → одна инструкция запуска и диагностика подключения; данные не удаляются при обычной остановке.

## Migration Plan

Существующих пользовательских данных нет. Реализация создаёт первую миграцию, volume и валидированный seed-пакет без перезаписи истории при повторном запуске. Порядок запуска: зависимости и окружение → PostgreSQL → миграции → проверка пакета → сервер/UI → eval → сквозная приёмка.

Для отката остановить приложение и вернуть предыдущую сборку; volume сохранять. Перед последующими миграциями делать backup. Сброс базы не является обычным способом отката и требует отдельного решения владельца.

## Open Questions

- Какой именно SHA документации закрепить: выбрать и проверить в задаче подготовки источников до написания заданий.
- Доступен ли выбранный snapshot в API-аккаунте пользователя: проверить при настройке; при недоступности выбрать совместимую модель и повторить тот же quality gate.
- Конкретные версии зависимостей и номера локальных портов: фиксируются при scaffold, не меняя архитектуру и поведение.

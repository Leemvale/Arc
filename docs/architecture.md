# Архитектура Arc

Arc — небольшое приложение с React-клиентом и Fastify-сервером. Модули разделяются
по обязанности и пользовательской функции. Общий код появляется при реальном
повторном использовании; отдельный слой не нужен для каждого вызова функции.

## Клиент

```text
src/
  main.tsx                  # точка входа, React и провайдеры
  app/App.tsx               # оболочка и выбор страницы
  features/
    track/                  # обзор трека и история
      index.ts              # публичный интерфейс функции
      TrackPage.tsx
      api.ts
      useTrack.ts
    practice/               # прохождение тренировки и результаты
      index.ts
      SessionPage.tsx
      api.ts
      useSession.ts
      useStartSession.ts
      useAnswerForm.ts
      useAnswerDraft.ts
      components/
  shared/
    api/request.ts          # общий HTTP-транспорт
    lib/                    # дата и hash-навигация
    ui/                     # общие компоненты без знания страниц
```

Направление зависимостей: `app → features → src/shared`; каждый из них может
использовать доменные правила и контракты из корневого `shared`.
Обратные зависимости запрещены. Клиент не импортирует сервер и учебные данные
из `content`: получает публичные данные через API, без закрытых рубрик оценивания.

Каждый файл компонента содержит один основной компонент. Страница объединяет
состояния загрузки, ошибки и содержимое. Компоненты отображают данные и вызывают
переданные действия или специализированные хуки. API-модуль определяет типизированные
запросы; хуки управляют React Query и побочными эффектами. Ключи и обновление кэша
сессии находятся вместе в `useSession`; запуск новой сессии — в `useStartSession`.
Сохранение и ошибки черновика принадлежат `useAnswerDraft`.

Одна функция может использовать другую через её `index.ts`, если зависимость
однонаправленная. Сейчас `track` использует публичный `useStartSession` из `practice`.
Внутри функции импортируйте конкретные файлы, чтобы её собственный `index.ts`
не создавал циклы. Не экспортируйте внутренние детали «на всякий случай».

## Сервер и общая модель

```text
server/app.ts       # сборка сервера
server/http/        # Host/Origin, ошибки, статические файлы
server/routes/      # URL, валидация входа, HTTP-статус и вызов операции
server/sessions.ts  # операции сессии и их транзакции
server/track.ts     # получение обзора трека
server/health.ts    # проверка доступности БД
server/worker.ts    # выполнение и восстановление фоновых попыток
server/assessor.ts  # адаптер AI-оценивания
server/db.ts        # соединение и транзакционный примитив
shared/domain.ts   # чистые правила, схемы и доменные типы
shared/contracts.ts # общие типы ответов API
content/           # серверные учебные данные и примеры оценки
```

Маршрут проверяет вход и вызывает операцию, но не выполняет SQL. Операции не
импортируют HTTP-слой. `shared` не зависит от клиента, сервера или учебных данных
и не выполняет ввод-вывод. Типы ответов API определяются один раз; представления
не получают внутренние типы строк БД или секреты провайдера.

SQL пока находится рядом с транзакционными операциями в серверных модулях.
Это осознанная граница текущего размера проекта: отдельные repositories следует
выделять при повторении запросов или независимой сложности хранения. При таком
выделении передавайте существующий транзакционный клиент; не разбивайте атомарные
операции на независимые транзакции.

## Размер и размещение изменений

- Новый экран добавляется в соответствующую функцию, а в `App` — только его маршрут.
- Новый запрос добавляется в `api.ts` функции, состояние запроса — в её хук.
- Новый серверный endpoint добавляется в маршруты, его операция — в серверный модуль.
- Повторно используемый UI без предметной логики переносится в `src/shared/ui`.
- Файл свыше 250 строк — сигнал проверить обязанности. Не дробите таблицы данных,
  схемы или связную операцию только ради числа строк. Не собирайте несвязанный код
  в общий `utils.ts`.
- Общий `styles.css` пока хранит небольшой визуальный стиль приложения. Стили новой
  самостоятельной функции размещайте рядом с ней; глобально оставляйте токены,
  базовые элементы и общую оболочку.

## Автоматические проверки

`npm run architecture:check` использует dependency-cruiser и запрещает циклы,
неразрешимые импорты, обратные зависимости слоёв, обход публичного интерфейса
функций, SQL-зависимости маршрутов и зависимости серверных операций от HTTP.
Правила публичных интерфейсов автоматически применяются к новым папкам `features`.
Конфигурация: `.dependency-cruiser.cjs`.

`npm run check` проверяет форматирование, архитектуру и TypeScript. Эта же команда
запускается в CI. Границы ответственности внутри функций дополнительно проверяются
при ревью: анализ импортов не способен оценить смысл каждой функции или SQL-строки.

Рефакторинг должен сохранять маршруты, API, кэш, черновики и транзакционные гарантии.
Проверяйте его существующими доменными, интеграционными и браузерными тестами.

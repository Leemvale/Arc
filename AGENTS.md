# Правила разработки Arc

Перед изменением структуры прочитайте `docs/architecture.md`.

- `src/app` собирает приложение. Не размещайте здесь страницы, запросы и бизнес-логику.
- Пользовательские функции живут в `src/features/<feature>`. Снаружи импортируйте
  только их публичный `index.ts`; внутри используйте прямые импорты.
- Один основной React-компонент на файл. Запросы и управление асинхронным состоянием
  выносите из JSX в API-модули и специализированные хуки. Черновики и другие побочные
  эффекты также отделяйте от отображения.
- `src/shared` содержит повторно используемые UI-примитивы, транспорт и утилиты,
  но не знает о функциях приложения. `shared` в корне содержит общие доменные
  правила и API-контракты без React, Fastify и доступа к внешним системам.
- `server/app.ts` только собирает сервер. HTTP-маршруты находятся в `server/routes`,
  общие HTTP-настройки — в `server/http`. SQL и бизнес-операции не пишите в маршрутах.
- Не создавайте циклические импорты и универсальные файлы `utils.ts`/`helpers.ts`
  для несвязанных обязанностей. Файлы более 250 строк требуют проверки разделения
  обязанностей; это ориентир для ревью, а не повод механически дробить данные и схемы.
- Сохраняйте транзакционные границы и существующие гарантии повторных запросов.
- Перед завершением запускайте `npm run check` и `npm test`. После изменения UI
  или взаимодействия с API запускайте `npm run build && npm run test:browser`.
  Браузерные и интеграционные тесты требуют локальный PostgreSQL.
- Используйте `npm run format`. Архитектурные исключения сначала обоснуйте в
  `docs/architecture.md`; не отключайте проверки ради прохождения CI.
